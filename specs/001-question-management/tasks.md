## 1. 기존 등록 오류 수정

기존 저장 경로를 유지하면서 사용자에게 영향을 주는 오류부터 고친다.

- [x] **T01. 입력 검증·테스트 환경 준비**
  - Zod, Vitest, Testing Library, user-event, jest-dom, jsdom을 추가하고 Vitest 설정·테스트 초기화 파일을 구성한다.
  - `test`는 개발 중 실행, `test:run`은 단발 실행으로 정의한다. 테스트 파일도 타입·린트 검사에 포함한다.
  - **완료 조건:** T02~T03의 테스트가 실제 실행되고 타입·린트 검사 대상에서도 빠지지 않는다. 설정 확인용 빈 테스트는 만들지 않는다.

- [x] **T02. 입력·중복·파일 처리 규칙 구현**
  - `src/features/questions/model/`에 스키마, 중복 비교, 파일 해석, 제외 사유·개수 계산을 구현한다.
  - 기존 일괄 등록·편집의 중복 버그를 수정 전 재현하고, 같은 조건을 새 규칙의 회귀 테스트로 연결한다.
  - **검증:** [spec 3.1](spec.md#31-입력과-중복)의 비교 예시와 [3.3](spec.md#33-파일-양식과-등록)의 파일 예시·집계 기준을 단위 테스트한다. 편집 대상 자신 제외, 원본 줄 번호, 원문 보존도 확인한다.

- [x] **T03. 기존 등록·편집 화면에 공통 규칙 적용**
  - `questionSlice.ts`의 직접 등록·일괄 등록·편집에 T02 규칙을 적용하고, 폼과 파일 화면에 거절 사유를 전달한다.
  - 빈 질문과 중복을 구분해 안내한다. 파일 미리보기 UI는 T07에서 추가한다.
  - **검증:** [spec 4](spec.md#4-동작-확인-기준) A01·A05·A06의 입력·중복 판정과 결과 안내를 확인한다. 기존 조회·삭제·면접 시작도 계속 동작해야 한다.

**단계 완료:** 저장 방식은 그대로이며, 직접 입력·파일 등록·편집에 같은 규칙이 적용된다.

## 2. Mock·API 준비

T03 이후 진행한다. 새 요청 경로는 준비하되 앱 화면은 아직 기존 저장 경로를 사용한다.

- [x] **T04. Mock DB와 MSW API 구현**
  - MSW를 추가하고 `src/mocks/`에 저장 어댑터·핸들러·브라우저/Node 시작 코드를 구성한다. 브라우저 worker는 `public/mockServiceWorker.js`에 생성한다.
  - [plan 3.3](plan.md#33-저장-키와-mock-db)의 저장 방식과 [4절](plan.md#4-api-계약)의 전체 API 계약을 구현한다. T02 규칙을 재사용한다.
  - [plan 5절](plan.md#5-mock-실행과-실패-재현)의 정상·지연·실패·중복 시나리오를 메서드·경로·횟수로 제어한다.
  - **검증:** 격리된 저장 어댑터로 저장 후 다시 읽기, 일괄 등록의 전체 반영, ID 증가, 지연된 중복 요청의 최종 판정을 확인한다. 화면 안내 검증은 3단계에서 수행한다.

- [x] **T05. API 함수와 Query 요청 훅 구현**
  - TanStack Query를 추가하고 `src/shared/api/`, `src/features/questions/api/`, `hooks/`에 요청·응답 검증, 오류 변환, 조회·변경 훅을 구현한다.
  - [plan 3.2](plan.md#32-query-갱신)와 [4절](plan.md#4-api-계약)에 따라 캐시 갱신과 오류 처리를 연결한다. 화면 메시지·이동은 API 함수에 넣지 않는다.
  - **검증:** 잘못된 응답 형식과 HTTP 오류를 성공 값으로 바꾸지 않는지 확인한다. 요청 상태·재조회·재시도는 T07~T08에서 실제 Query와 MSW를 연결해 검증한다.

**단계 완료:** 새 API 경로가 준비됐고 기존 화면 동작은 유지된다.

## 3. 화면과 데이터 경로 전환

T04~T05 이후 진행한다. T06~T08은 하나의 전환 범위이며, 일부 화면만 API를 사용하는 상태로 완료하지 않는다.

- [x] **T06. 모든 질문 읽기·쓰기를 API로 연결**
  - `main.tsx`에서 MSW 시작을 기다린 뒤 QueryClientProvider로 앱을 렌더링한다. dev·build/preview·서버 모드 분기는 [plan 5절](plan.md#5-mock-실행과-실패-재현)을 따른다.
  - 질문 폼·파일·목록·편집·삭제, `SetupPage.tsx`, `CategoryFilter.tsx`를 같은 Query 목록에 연결한다.
  - `useCategoryStore`를 분리하고 `startSession(questions, filterCategory)`로 세션에 질문 복사본을 전달한다. 사용처를 전환한 뒤 질문 slice와 기존 persist 연결을 제거한다.
  - **검증:** 질문을 기존 스토어·브라우저 저장에서 직접 읽거나 쓰는 경로가 남지 않아야 한다. 변경된 질문이 목록·개수·면접 시작에 일치하고 기존 저장 데이터는 건드리지 않아야 한다.

- [x] **T07. 직접 등록·파일 등록 흐름 완성**
  - 직접 등록에 처리 상태·반복 제출 방지·입력 유지·재시도를 연결한다.
  - 파일 양식 안내·예시 다운로드·카테고리 선택·미리보기·등록 확인·최종 결과를 구현한다. 이전 파일의 늦은 읽기 결과가 새 선택을 덮지 않게 한다.
  - **검증:** Testing Library + MSW로 [spec 4](spec.md#4-동작-확인-기준) A01~A04·A06·A13~A17을 확인한다. 결과 안내뿐 아니라 반복 제출·자동 재전송 여부도 요청 횟수로 확인한다.

- [x] **T08. 조회·편집·삭제·면접 연결 검증**
  - 초기 조회·재조회·빈 목록·빈 필터 상태와 편집·개별/전체 삭제의 성공·실패 처리를 완성한다.
  - 세션 시작 후 질문 목록이 재조회되어도 진행 중 세션은 바뀌지 않도록 한다. 카테고리 저장·복원은 R38을 따른다.
  - **검증:** Testing Library + MSW로 [spec 4](spec.md#4-동작-확인-기준) A05·A07·A18, [3.4](spec.md#34-조회편집삭제면접-시작) R26~R32·R38의 미포함 조건을 확인한다. 변경 요청의 응답 유실 처리도 편집·삭제에 적용됐는지 확인한다.

**단계 완료:** 모든 질문 기능이 같은 API 데이터를 사용하고, 등록부터 면접 시작까지 연결된다.

### 5.2. 후속 리뷰와 수정

#### 특수 이름의 카테고리 개수 수정

카테고리별 개수는 이번에 유지하기로 한 기능이므로, 알려진 오류로 남기지 않고 수정했다. 일반 객체의 기본 속성과 카테고리 이름이 충돌하는 집계를 `Map<string, number>`로 바꿨다. 질문 저장 방식과 카테고리 이름 규칙은 변경하지 않았다.

| 확인 조건 | 기대 결과 | 실제 결과 |
| --- | --- | --- |
| `__proto__`·`constructor`·`toString` 추가 | 질문이 없으면 0 표시 | 추가한 화면 테스트 3개가 수정 전 모두 실패, 수정 후 통과 |
| 각 카테고리에 두 질문 등록 → 필터 선택 → 하나 삭제 | 0 → 1 → 2 → 1, 다른 카테고리 개수 유지 | 실제 API·MSW를 연결한 같은 테스트에서 개수·필터 목록 일치 |

재현·회귀 명령: `npm run test:run -- src/features/questions/components/questionManagement.test.tsx -t '카테고리 이름'`. 전체 검사 결과는 5.1절에 기록했다.

#### 최종 교차 리뷰

과제 요구사항·AI 설명, 구현, 문서와 검증 기록을 각각 AI에 나눠 검토하도록 요청했다. 과제 원문에 비춰 필요한 설명이 있는지 확인하고, 코드 지적은 재현 조건과 사용자 영향을 대조했다. README는 작성자인 제 판단을 중심으로 유지하되 실제 실행·재현을 AI에 맡긴 부분을 구분했다.

| 확인 조건 | 기대 결과 | 실제 결과 | 판정 |
| --- | --- | --- | --- |
| A02: 등록 지연 중 Enter 2회·마우스 더블클릭 | POST 1회, 선택 카테고리·필터 유지 | 별도 Chromium 컨텍스트에서 POST 1회, 프론트엔드 선택·백엔드 필터 유지 | 통과 |
| 개별 삭제 실패 후 사용자 재시도 | 첫 실패 요청 1회, 재시도 후 총 2회 | Chromium에서 실패 안내·질문 유지 후 직접 재시도, DELETE 총 2회·질문 삭제 | 통과 |
| 삭제 지연 → 필터 왕복 → 500 실패 | 질문 유지와 실패·재시도 안내 | 수정 전 안내가 사라짐. 수정 후 필터 복귀 전·후 실패 모두 안내 유지, 사용자 재시도 시에만 추가 요청 | 수정·검증 완료 |
| `__proto__` 카테고리 추가 → 질문 등록 | 등록 전 0, 등록 후 1 | 두 경우 모두 `[object Object]` 표시. 원본 커밋에도 같은 집계 방식 존재 | 기존 문제 확인 |

삭제 실패 안내는 행 컴포넌트의 로컬 오류 상태가 필터 변경으로 사라지는 문제다. 진행 중 상태만 Query에서 공유하므로 재시도 잠금은 정상적으로 풀린다. 카테고리 개수는 일반 객체의 기본 속성과 이름이 충돌하는 문제다. 두 경우 모두 질문 데이터 유실은 없었다. 당시 삭제 실패 안내를 먼저 수정하고 카테고리 개수 오류는 남겼으나, 이후 위의 회귀 테스트로 재현해 수정했다.


#### 필터 변경 후 삭제 실패 안내 유지

삭제 요청은 계속 진행되지만 필터를 바꾸면 질문 행이 제거돼 오류 안내가 사라졌다. 안내를 `QuestionList`에서 질문 ID별로 보관하도록 변경했다. 재시도를 시작하면 해당 질문의 안내만 지우고, 전체 삭제가 성공하면 모든 삭제 안내를 정리한다.

| 확인 조건 | 방법·기대 결과 | 실제 결과 |
| --- | --- | --- |
| 필터 복귀 전·후에 삭제 실패 | MSW 응답 시점을 제어한 화면 테스트. 질문·개수·실패 안내 유지 | 수정 전 두 테스트 모두 안내가 없어 실패. 수정 후 모두 통과 |
| 실패 후 필터 재변경·사용자 재시도 | 다른 질문에는 오류가 없어야 하며 자동 요청 없이 사용자 재시도 때만 전송 | 안내 유지·오류 구분, 첫 실패 1회와 재시도 1회 확인. 성공 후 질문·안내 제거 |
| Chromium에서 같은 조작 | 앱의 MSW에 500을 설정하고 DELETE 전송을 보류한 뒤 필터 왕복·요청 해제 | 실패 안내 유지, 다시 필터를 바꿔도 유지. 사용자 재시도 후 삭제 성공·DELETE 총 2회 |

`npm run test:run` 99개, `npm run test:e2e` 4개와 빌드, 타입 검사·변경한 세 코드 파일의 린트가 통과했다. `npm run check`는 기존 녹음·세션 린트 오류 1건·경고 2건으로 중단됐다.


#### 오프라인 요청과 재시도 검증

피드백을 검토하며 AI에 오프라인 전환 재현을 맡겼다. `retry: false`여도 최초 요청은 보류될 수 있었다. 기존 코드에서는 오프라인 등록 시 요청 0회인 채 입력이 잠겼고, 연결 복구 후 사용자 조작 없이 POST가 전송됐다.

| 확인 조건 | 기대 결과 | 실제 결과·수정 |
| --- | --- | --- |
| 수정 전 오프라인 조회 | Mock이 즉시 응답 | 새 Query 연결 테스트와 E2E 모두 조회가 대기해 실패 |
| 수정 후 오프라인 조회·변경 | 연결 상태와 관계없이 Mock 요청 실행 | 공통 QueryClient의 조회·변경을 `networkMode: always`로 설정. 같은 실패 테스트 통과, 오프라인 등록·일괄 등록·편집·개별/전체 삭제 확인 |
| 오프라인 등록 실패 → 연결 복구 | 입력 유지·잠금 해제, 사용자 재시도 전 등록 없음 | Chromium에서 POST 1회 유지. 오프라인 상태에서 사용자가 재시도한 뒤 2회, 다시 연결해도 2회 유지 |
| fetch 실패 → 연결 복구 | 결과 확인 불가 안내, 자동 전송 없음 | 테스트 핸들러의 네트워크 오류와 Query 연결 상태 전환으로 요청 1회 유지 확인 |
| 직접·파일 등록·전체 삭제 실패 후 재시도 | 첫 실패 1회, 사용자 재시도 후 총 2회 | 각 화면 테스트에 변경 요청 횟수 검증 추가, 통과 |

앱과 테스트가 같은 QueryClient 생성 함수를 사용하도록 연결했다. `networkMode`는 [공식 문서](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode)와 설치된 코드, 수정 전·후 실행으로 확인했다. 브라우저 오프라인 테스트는 MSW 환경이며 실제 서버와의 통신 장애 검증은 아니다.

기존 카테고리 미복원도 별도 브라우저 컨텍스트에서 확인했다. 이전 키에 사용자 카테고리만 저장해도 현재 화면은 기본 카테고리로 시작했고 원본은 보존됐다. 이전 기능을 추가하지 않고 README·spec·plan에 이 영향을 명시했다.

#### 제출 전 리뷰 — 요청 중 추가 조작과 키보드 흐름

구현 후 AI에 추가 리뷰를 요청했다. 리뷰에서 개별 성공·실패뿐 아니라 요청 중 다른 기능을 조작하는 흐름도 확인했다. AI가 코드 분석과 브라우저 재현을 수행했고, 재현 결과를 근거로 수정을 진행했다.

| 조건 | 수정 전 결과 | 수정과 확인 | 판정 |
| --- | --- | --- | --- |
| 전체 삭제 지연 중 새 질문 등록 | 새 질문의 등록 성공 후 전체 삭제가 완료되며 새 질문도 사라짐 | 전체 삭제와 다른 변경 요청을 서로 차단. 입력 보존·완료 후 등록과 반대 순서도 통합 테스트로 확인 | 통과 |
| 삭제 중 다른 필터로 이동 후 복귀 | 삭제 버튼 재활성화, 동일 대상 DELETE 2회 | 질문 ID별 Query mutation 상태 구독. 필터 왕복 후 잠금 유지·DELETE 1회 확인 | 통과 |
| 입력창에서 Enter 제출 후 다음 질문 입력 | 요청 중 초점이 사라져 후속 키보드 입력 불가 | 처리 후 초점 복원. Playwright에서 연속 입력과 사용자가 옮긴 초점을 뺏지 않는지 확인 | 통과 |

- 새 통합 테스트 3개는 수정 전 실패, 수정 후 통과했다. 키보드 문제는 수정 전 브라우저 재현 후 E2E에 추가해 수정 결과를 확인했다.
- `npm run test:run`: 9개 파일·96개 통과. `npm run test:e2e`: Chromium 3개 통과(실제 빌드 포함).
- `npm run check`: 타입 통과, 기존 Recorder·SessionPage 린트 오류 1건·경고 2건으로 중단. `npx eslint src/features/questions src/pages/SetupPage.tsx e2e --max-warnings 0`: 통과.
- 요청 상태를 Zustand에 추가하지 않고 Query mutation 캐시를 사용했다. 전체 화면을 잠그지 않고 전체 삭제와 충돌하는 변경만 막았으며, 필터 조회는 유지했다.

#### 문서 교차 검토 — 카테고리 복원

“Zustand 기본 동작으로 손상된 카테고리를 처리할 수 있다”는 검토 의견을 확인했다. AI가 설치된 `zustand/middleware.js`를 읽고, 임시 메모리 저장소로 기본 persist 동작을 실행했다. 깨진 JSON은 초기값을 유지했지만, 정상 JSON 안의 `categories: [5]`는 그대로 복원됐다. 기본 동작만으로 유효성을 보장한다는 설명은 채택하지 않았고, `useCategoryStore.ts`의 Zod 검증·기본값 처리를 유지했다. 코드 변경 없이 설명의 근거를 바로잡았다.

const { createQuestionSlice } = await import('data:text/javascript;base64,' + Buffer.from(code).toString('base64'));
const batch = createStore(createQuestionSlice);
batch.getState().addQuestions([{ text: '같은 질문' }, { text: '같은 질문' }]);
const edit = createStore(createQuestionSlice);
edit.getState().addQuestions([{ text: '질문 A' }, { text: '질문 B' }]);

JS
