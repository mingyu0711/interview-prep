# 001. 질문 등록·관리 개선 — 구현 계획

[spec](spec.md) · [tasks](tasks.md) · [개발 규칙](../../AGENTS.md) · [개발 절차](../../docs/development-workflow.md)

**데이터 흐름:** 화면 → Query 요청 훅 → API 함수 → MSW → Mock DB. 앱은 MSW 시작 후 질문 목록을 바로 조회한다.

## 1. 변경 전 코드와 적용 내용

| 변경 전 코드 | 적용 내용 |
| --- | --- |
| `questionSlice.ts` | 공통 입력 규칙부터 적용하고, API 전환 후 질문 slice 제거 |
| `useInterviewStore.ts`, `sessionSlice.ts` | 세션만 관리, persist 제거. `startSession(questions, filterCategory)`로 질문을 받아 복사 |

## 2. 코드 구조와 역할

| 위치 | 책임 |
| --- | --- |
| `features/questions/model/` | Zod 스키마·타입, 중복 비교·파일 해석·집계 순수 함수 |
| `features/questions/api/`, `hooks/` | HTTP 입출력 검증 / Query 조회·변경·캐시 갱신·파일 상태 |

## 3. 상태 관리와 데이터 저장

### 3.1. 상태를 관리할 위치

| 데이터 | 관리 위치 |
| --- | --- |
| 질문 | Query `['questions']`. 캐시 persist 없음 |
| 카테고리·세션 | Zustand. 카테고리만 persist, 세션은 시작 시 질문 복사본 사용 |
| 입력·편집·필터·파일 미리보기 | 화면·폼 로컬 상태 |
| 개별 삭제 실패 안내 | 필터 변경에도 유지되는 `QuestionList`에서 질문 ID별 관리. 재시도 시 해당 안내를 지우고 전체 삭제 성공 시 모두 정리 |
| 요청 상태 | Query mutation. 전역 상태에 복제하지 않음 |

### 3.2. Query 갱신

- 앱과 테스트는 `shared/api/queryClient.ts`의 생성 함수를 사용한다. 조회·변경 모두 `networkMode: always`로 연결 상태에 따른 요청 보류를 하지 않는다.
- 조회는 `retry: false`, `refetchOnWindowFocus: false`, 질문은 `staleTime: 0`.
- 변경 요청을 공통 mutation key로 묶고 진행 상태를 조회해, 전체 삭제와 다른 쓰기가 동시에 실행되지 않도록 화면과 제출 핸들러에서 막는다. 개별 삭제의 진행 상태는 질문 ID로 Query mutation 캐시에서 확인해 필터 변경에도 유지한다.
- 변경은 자동 재시도하지 않는다. 버튼·Enter를 같은 제출 경로로 연결하고 즉시 설정하는 가드로 연타를 막는다.
- 성공 후 질문 key를 invalidate한다. 낙관적 반영·응답 일부의 수동 병합은 하지 않는다. 저장 성공과 후속 조회 실패를 분리한다.

### 3.3. 저장 키와 Mock DB

| 대상 | localStorage 키 | 저장할 데이터 |
| --- | --- | --- |
| Mock DB | `interview-prep-mock-db-v1` | 질문 목록·다음 질문 ID·저장 형식 버전 |
| 카테고리 | `interview-prep-categories-v1` | 카테고리 목록. Zustand persist 사용, 버전 1 |

- **질문:** 처음에는 빈 목록으로 시작한다. 변경 결과를 하나의 JSON으로 저장하고, 새로고침하면 다시 불러온다. 저장이 끝난 뒤 성공 응답을 보내며, 실패 시 기존 데이터는 유지한다.
- **카테고리:** 저장된 목록을 불러온다. 값이 없거나 유효하지 않으면 기본 카테고리로 시작한다.
- **기존 데이터:** `interview-prep-store`의 질문·카테고리는 읽거나 수정·삭제하지 않는다. 새 저장 키가 없으면 빈 질문 목록·기본 카테고리로 시작하므로 이전 버전의 직접 만든 카테고리도 표시되지 않는다.

## 4. API 계약

### 4.1. 공통 데이터와 오류

기본 경로는 `/api`. 파일은 브라우저에서 해석하고 행을 전송한다. 요청·응답·저장 데이터를 Zod로 검증한다.

| 형식 | 필드 |
| --- | --- |
| `Question` | `id: number`, `text: string`, `category: string` |
| `QuestionInput` | `text: string`, `category: string` |
| `BatchRow` | `line: number`, `text: string`, `category: string` — 원본 줄 번호 |
| `BatchResult` | `added: Question[]`, `excluded: { line, reasons: string[] }[]`, `summary: { total, added, duplicate, invalid }` |
| `ApiError` | `{ error: { code: string, message: string } }` |

질문 ID는 number 타입을 유지한다. `nextQuestionId`는 1부터 시작해 등록할 때 증가시키고 전체 삭제 후에도 초기화하지 않는다.

| 오류·흐름 | 오류 코드·화면 동작 | spec |
| --- | --- | --- |
| 400 입력·계약 오류 | `INVALID_REQUEST`. 입력 유지·오류 안내 | [3.2](spec.md#32-직접-등록과-요청-결과) `R09` |
| 404 편집 대상 없음 | `QUESTION_NOT_FOUND`. 삭제됨 안내·재조회·해당 대상 재저장 차단 | [3.4](spec.md#34-조회편집삭제면접-시작) `R24` |
| 409 중복 | `QUESTION_DUPLICATE`. 입력 유지·중복 안내·잠금 해제 | [3.2](spec.md#32-직접-등록과-요청-결과) `R08` |
| 500 변경 요청 | `MOCK_DB_UNAVAILABLE` / `INTERNAL_ERROR`. 저장 전 실패, 입력 유지·사용자 재시도 | [3.2](spec.md#32-직접-등록과-요청-결과) `R09` |
| 네트워크·응답 형식 오류 | 변경은 결과 확인 불가 안내·목록 새로고침. 조회는 기존 데이터 유지·재조회 | [3.2](spec.md#32-직접-등록과-요청-결과) `R09`, [3.4](spec.md#34-조회편집삭제면접-시작) `R26`~`R27` |
| 조회의 HTTP 오류 | 조회 실패 안내와 재시도 제공. 기존 데이터가 있으면 유지 | [3.4](spec.md#34-조회편집삭제면접-시작) `R26`~`R27` |

### 4.2. 질문 조회·변경

| 메서드·경로 | 요청 | 성공 응답 |
| --- | --- | --- |
| `GET /questions` | 없음 | 200 `{ questions: Question[] }` — 등록 순서 |
| `POST /questions` | `QuestionInput` | 201 `{ question: Question }` |
| `POST /questions/batch` | `{ items: BatchRow[] }` | 200 `BatchResult` — 추가 0개도 결과 반환 |
| `PATCH /questions/:id` | `QuestionInput` — 두 필드 모두 | 200 `{ question: Question }` |
| `DELETE /questions/:id` | 없음 | 204 — 이미 없어도 완료 |
| `DELETE /questions` | 없음 | 200 `{ deletedCount: number }` — 전체 삭제 |

- 일괄 등록은 빈 줄을 제외한 모든 행을 보낸다. line 순서대로 오류 → 기존 중복 → 파일 내부 중복을 판정하고 유효 항목 전체를 한 번에 저장한다.
- 행별 제외 코드는 `EMPTY_TEXT`, `EMPTY_CATEGORY`, `ALREADY_EXISTS`, `DUPLICATE_IN_FILE`. 빈 질문·카테고리는 두 사유를 표시해도 오류 1개로 센다. 배열 형식·줄 번호 중복 등 계약 오류만 400으로 처리한다.
- 파일은 첫 `::`·CRLF/LF·UTF-8 BOM을 처리한다. 선택마다 식별자를 바꿔 이전 파일의 늦은 읽기 결과를 무시하며 예시는 정적 `.txt`로 제공한다.

### 4.3. 응답을 받지 못한 경우

입력을 유지하고 확인 불가를 안내한다. 자동 재전송 없이 사용자가 목록을 확인한 뒤 재시도한다. 조회로 원래 요청의 성공을 확정하지 않는다.

## 5. Mock 실행과 실패 재현

MSW는 dev·build/preview에서 사용하고 `worker.start()` 후 앱을 렌더링한다. 실제 서버 모드는 실행·빌드 전 `VITE_API_MODE=server`로 지정한다. `window.__questionMock.setScenario(...)`에 대상 메서드·경로·횟수를 지정하며 데이터는 초기화하지 않는다.

설정 형식은 `{ method: 'POST', path: '/api/questions', scenario: 'error', times: 1 }`이다. `scenario`는 `normal`·`delay`·`error`, `times`의 기본값은 1이다. 메서드와 정확한 경로가 일치하는 요청에만 적용하며 `normal`은 해당 설정, `reset()`은 모든 시나리오 설정만 해제한다.

| 시나리오 | 재현 |
| --- | --- |
| 정상·지연 | 정상 처리 또는 최신 DB 확인 전 1,500ms 대기 |
| 저장 전 실패 | 대상 요청 1회 500, 질문 변경 없음 |
| 후속 조회 실패 | 저장 성공 후 다음 질문 GET 1회 500 |
| 중복 거절 | 실제 충돌하는 질문으로 409 재현 |

`HttpResponse.error()`는 HTTP 오류 응답 대신 fetch 실패를 만든다. [MSW 문서](https://mswjs.io/api/http-response) 브라우저는 영속 저장 어댑터, Node는 격리된 메모리 어댑터와 `setupServer`로 같은 핸들러를 사용한다.

## 7. 선택 이유와 한계

| 선택 | 선택한 이유 | 남는 비용·한계 |
| --- | --- | --- |
| 질문은 Query, 세션·카테고리는 Zustand | 질문을 두 곳에 보관하면 변경할 때마다 양쪽을 맞춰야 함. API로 받는 질문은 Query에서만 관리 | 두 라이브러리의 역할을 구분해 사용해야 함 |
| 카테고리 목록은 로컬 유지 | 질문 등록 흐름에 집중하고 카테고리 API는 이번 범위에서 제외 | 질문에 기록된 카테고리 이름과 선택 가능한 목록이 별개다. 파일에만 있는 이름은 직접 추가해야 필터로 선택 가능. 실제 서버 연결 시 카테고리 API 또는 질문에서 목록을 계산하는 방식을 검토해야 함 |
| 연결 상태와 관계없이 요청 실행 | Mock은 네트워크 없이도 응답할 수 있음. 기본 `online` 모드는 요청을 보류한 뒤 연결 복구 시 실행하므로 사용자의 재시도 원칙과 맞지 않음 | 실제 서버에서는 fetch가 실패하면 오류로 안내해야 함. 연결 복구 시 변경 요청은 자동 실행하지 않음 |
| 저장 성공 후 목록을 다시 조회 | 화면에서 목록을 직접 고치는 대신 API의 최신 목록으로 갱신해 누락·불일치 가능성을 줄임 | 변경할 때마다 조회 요청이 한 번 더 필요 |
| Mock DB를 브라우저에 저장 | 메모리만 쓰면 새로고침 시 질문이 사라짐. 별도 서버 설치 없이 등록 결과를 유지하기 위한 선택 | 다른 기기와 공유할 수 없고, 브라우저 데이터를 지우면 사라짐 |
| 응답이 없을 때 자동 복구는 제외 | 요청 이력과 처리 결과를 추적하는 별도 기능까지 만들면 등록 개선의 범위를 벗어남 | 저장 여부를 확정할 수 없어 사용자가 목록을 확인한 뒤 재시도해야 함 |
