# 기능 개발 절차

여러 기능에 공통으로 적용하는 개발 규칙은 [AGENTS.md](../AGENTS.md)에, 한 기능의 정책·상태 코드·저장 키·검증 대상은 해당 기능 문서에 둔다.

**기능 개발을 시작할 때 `spec → plan → tasks` 순서로 작성한다.** 경로는 `specs/<번호>-<기능>/`로 정한다. 번호는 생성 순서대로 `001`부터 증가하는 3자리 숫자, 기능명은 영어 kebab-case를 사용한다. 예: `specs/001-question-api/`. 같은 기능을 수정할 때는 기존 번호와 폴더를 유지한다.

## 1. 문서 역할

| 문서 | 답할 질문 | 담을 내용 |
| --- | --- | --- |
| `spec.md` | 무엇이 어떻게 동작해야 하는가? | 사용자 흐름, 범위, 예외 동작, 완료 조건, 미정 정책 |
| `plan.md` | 어떻게 구현할 것인가? | 코드 경계, 상태 소유·persist 대상, API 계약·상태 코드, 저장 키, 선택 이유, 검증 방법 |
| `tasks.md` | 어떤 순서로 끝낼 것인가? | 작업 단위, 검증 대상, 진행 상태, 검증 기록 |

같은 내용을 세 문서에 복사하지 않는다. tasks는 spec·plan의 항목을 참조한다.

---

## 2. 진행 순서

1. **spec:** 합의한 동작과 완료 조건을 적는다. 정하지 않은 정책은 미정으로 남긴다.
2. **plan:** spec의 동작과 정책에 맞춰 구조·API 계약·검증 방법을 정한다. 중요한 선택은 대안과 비용을 짧게 비교한다.
3. **tasks:** 완료 단계마다 기존 사용 흐름이 동작하도록 작업을 나눈다. 코드 작성 단위는 나눠도, 기능이 일부만 전환된 상태를 완료 단계로 삼지 않는다. 버그 재현의 실패는 수정 과정에서 확인하고, 관련 검사를 통과한 상태를 완료로 커밋한다.
4. **구현·검증:** 실제 결과를 기록한다. 실행하지 않은 항목은 완료로 표시하지 않는다.

미정 정책에 의존하는 작업은 확정 후 진행한다. 합의한 범위는 단계마다 재승인받지 않는다.

---

## 3. 기록과 유지

- 검증은 `조건 / 명령 또는 조작 / 기대 결과 / 실제 결과 / 판정`으로 tasks에 기록하고, 핵심 결과를 README의 확인 결과 항목에 요약한다.
- AI가 생성한 결과를 검토·수정한 사례는 작업하면서 tasks에 적는다. 전달한 맥락, 채택·수정 이유, 확인 방법을 남긴다.
- 같은 기능을 바꾸면 기존 문서를 갱신한다. 빈 템플릿이나 컴포넌트별 문서를 만들지 않는다.
- 국소 버그는 재현 → 수정 → 회귀 확인으로 처리한다. 기대 동작이 바뀌면 spec을 갱신한다.
- README에는 구현된 내용과 확정된 결정만 요약한다.
