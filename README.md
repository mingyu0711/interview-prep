## 1. 서비스 소개와 선택 이유

| 항목 | 내용 |
| --- | --- |
| 사용자와 목적 | 혼자 면접을 준비하는 사람이 예상 질문을 등록하고, 무작위로 출제되는 질문에 답변을 녹음하며 연습하는 React 웹 서비스 |
| 개발 배경 | 면접 질문 정리와 답변 연습을 위해 AI로 빠르게 구현. 별도 DB 서버 없이 브라우저에 질문을 저장하는 방식으로 시작 |
| 발견한 문제 | 파일 등록·질문 편집 시 같은 질문이 중복 저장됨. 파일 등록에서 빈 질문과 중복 질문을 구분하지 않고 모두 ‘중복 제외’로 안내 |
| 선택 이유 | 직접 면접 연습에 쓰려고 만든 앱이며, 등록 오류가 연습할 질문 목록에도 영향을 줌. 질문 등록과 결과 안내를 개선하기 위해 기존 앱을 선택 |

<br>

## 2. 핵심 흐름과 요구사항

**질문 등록 → 결과 확인 → 등록한 질문으로 면접 연습**

| 조건 | 기대 동작 |
| --- | --- |
| 정상 등록 | 목록에 반영되고 새로고침 후에도 유지 |
| 빈 질문·중복 | 직접 입력·파일·편집에 같은 기준 적용. 파일은 제외한 줄과 이유 안내 |
| 파일 선택 | 저장할 질문을 먼저 보여주고, 등록 버튼을 눌렀을 때 저장 |
| 요청 실패·반복 조작 | 실패 시 입력 보존과 재시도 안내, 처리 중 중복 요청 차단 |

세부 입력 예시와 동작 기준은 [spec](specs/001-question-management/spec.md)에 정리했습니다.

## 3. 작업 범위

- **기존 앱:** AI를 활용해 구현한 `616e72f`까지의 코드
- **개발 환경 정비:** [PR #1](https://github.com/mingyu0711/interview-prep/pull/1)
- **이번 기능 개선:** [PR #2 — 질문 등록 검증·파일 미리보기와 API 전환](https://github.com/mingyu0711/interview-prep/pull/2) (`6b8e97e` 기준 변경)

등록 결과를 정확히 알리고, 실패해도 입력을 다시 작성하지 않도록 질문 등록에 집중했습니다. 저장 방식이 바뀌어도 기존 기능을 유지하도록 조회·편집·삭제·면접 시작을 함께 연결했습니다.

| 범위 | 내용 |
| --- | --- |
| 핵심 개선 | 직접 등록·편집의 입력 검증, 파일 양식·예시·미리보기·등록 결과 |
| 데이터 처리 | API + MSW·TanStack Query로 전환, 새로고침 후 저장 유지 |
| 기존 기능 연결 | 조회·개별/전체 삭제·카테고리별 개수·면접 시작 |
| 제외 | 기존 데이터 이전, 실제 백엔드·로그인, 면접 진행·녹음 개선·복원, 필터 URL 유지. 영향과 이유는 [7.2절](#72-남은-일과-미룬-이유)에 정리 |

파일 파싱은 브라우저에서 처리할 수 있어 API로 옮기지 않았습니다. [질문 기능](src/features/questions/)과 [목록·면접 시작 연결](src/pages/SetupPage.tsx)이 주요 변경 대상입니다.

## 4. 실행 및 확인 방법

### 4.1. 실행 환경과 시작 방법

| 항목 | 내용 |
| --- | --- |
| 개발 환경 | Node.js `24.15.0`, npm `11.12.1` |
| 의존성 | [package.json](package.json), [package-lock.json](package-lock.json) |
| 추가 설정 | 별도 서버·API 키 불필요. 녹음 시 브라우저 마이크 권한 필요 |
| 파일 입력 예시 | `.txt`의 한 줄이 질문 하나. `일반::자기소개를 해주세요.`로 카테고리 지정 가능 |

저장소 루트에서 실행합니다.

```bash
npm ci
npm run dev
```

- **서버 실행:** 별도 서버 불필요. dev·build/preview 모두 MSW가 API 요청에 응답합니다.
- **시작 데이터:** 새 저장 데이터가 없으면 빈 질문 목록과 기본 카테고리로 시작합니다.
- **이전 버전 데이터:** 기존 질문·카테고리는 가져오지 않으며 원본은 변경하지 않습니다.

### 4.2. 핵심 흐름 확인

터미널에 표시되는 주소로 접속합니다. 아래 예시는 질문이 없는 상태를 기준으로 합니다. 데이터가 이미 있다면 다른 브라우저 프로필에서 실행하거나 보관할 질문이 없는 경우에만 전체 삭제합니다.

아래 내용을 `questions.txt`로 저장합니다.

```text
react란
자기소개를 해주세요
자기소개를  해주세요?
일반::
```

| 순서 | 조작 | 확인할 결과 |
| --- | --- | --- |
| 1 | 직접 입력으로 `React란?` 등록 | 목록에 질문 1개 표시 |
| 2 | **텍스트 파일 선택**에서 위 파일 선택 | 등록 가능 1개·중복 2개·입력 오류 1개. 줄별 제외 사유 표시, 아직 저장하지 않음 |
| 3 | **등록 가능한 1개 추가** 클릭 | 자기소개 질문만 추가. 실제 등록·제외 결과 표시 |
| 4 | 새로고침 후 **일반** 카테고리 선택 | 질문 2개 유지 |
| 5 | **면접 시작** 클릭 | 선택한 카테고리의 질문으로 면접 시작 |

화면의 **예시 파일 다운로드 (.txt)**로 정상 파일 등록도 확인할 수 있습니다.

<details>
<summary><strong>4.3. 실패·지연 상황 확인</strong></summary>

브라우저 개발자 도구 콘솔에서 **확인할 명령 하나를 실행한 뒤** 해당 화면을 조작합니다. 각 설정은 일치하는 다음 요청 1회에만 적용되며 저장된 질문은 지우지 않습니다.

**직접 등록 지연:** 아래 명령 실행 → 아직 등록하지 않은 질문 입력 → 추가. 1.5초 동안 입력·제출이 잠기고, 반복 조작해도 한 번만 등록됩니다.

```js
window.__questionMock.setScenario({ method: 'POST', path: '/api/questions', scenario: 'delay' })
```

**파일 등록 실패:** 등록 가능한 파일을 선택해 미리보기 표시 → 아래 명령 실행 → 등록. 저장 없이 오류를 안내하며, 파일을 다시 선택하지 않고 재시도하면 저장됩니다.

```js
window.__questionMock.setScenario({ method: 'POST', path: '/api/questions/batch', scenario: 'error' })
```

**저장 후 목록 갱신 실패:** 아래 명령 실행 → 새 질문 등록. 등록 성공과 목록 갱신 실패를 따로 안내하며, **목록 새로고침**을 누르면 저장된 질문이 나타납니다.

```js
window.__questionMock.setScenario({ method: 'GET', path: '/api/questions', scenario: 'error' })
```

사용하지 않은 시나리오 설정은 `window.__questionMock.reset()`으로 해제합니다.

## 5. 주요 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 공통 입력 규칙 | 직접 등록·파일·편집에서 같은 질문을 다르게 판단하지 않도록 통일 |
| 저장 직전 중복 재검사 | 미리보기 이후 목록이 바뀌어도 실제 저장 데이터를 기준으로 판단 |
| API + MSW | 추후 서버 연결 시 화면 변경을 줄이도록 데이터 접근을 분리. MSW로 지연·실패를 재현 |
| Query / Zustand 분리 | 질문은 Query에서만 관리해 복제·동기화를 피함. 세션·카테고리는 Zustand 유지 |

Mock DB는 브라우저에 저장해 새로고침 후에도 유지합니다. 기기 간 동기화는 제공하지 않습니다. [대안과 비용 비교](specs/001-question-management/plan.md#7-선택-이유와-한계)

## 6. AI 활용과 판단

질문 등록에서 개선할 문제를 먼저 제기하고, AI에 기존 등록·파일 업로드·편집 코드를 분석하도록 요청했습니다. 분석·설계안은 다른 AI로 교차 검토하되, **등록 흐름에 필요한 변경인지, 기존 기능에 어떤 영향을 주는지**를 기준으로 수정 범위를 정했습니다.

| 단계 | AI가 수행한 작업과 결과 | 채택·수정한 기준 |
| --- | --- | --- |
| 요구사항 정리 | 등록·파일·편집에 적용할 중복 기준 후보와 예외를 [spec](specs/001-question-management/spec.md) 초안으로 정리 | 대소문자·공백·끝 물음표 차이는 중복으로 처리하되, 의미가 달라지는 기호는 구분. 비교에만 적용하고 저장 문장은 보존 |
| 구현 순서 | [설계](specs/001-question-management/plan.md)를 [작업 목록](specs/001-question-management/tasks.md)으로 나누고 단계별 구현·테스트 수행 | 기존 앱에서 중복 등록·편집 오류를 먼저 고치고 검증한 뒤 API를 연결. 한꺼번에 바꾸면 중복 검사와 API 연결 중 어디서 문제가 생겼는지 찾기 어려워 순서를 나눔 |
| 구현 후 리뷰 | 추가 리뷰에서 전체 삭제를 지연시키고 등록을 실행해, 새 질문까지 삭제되는 문제 재현 | 충돌하는 등록·편집·삭제 요청만 차단하는 수정을 채택. 필터 조회는 유지하고, 작성한 질문은 삭제 완료 후 다시 입력할 필요가 없도록 보존 |
| 결과 검토 | spec 기준 테스트와 브라우저 검증을 실행하고, 버그 수정 전 실패·수정 후 통과 결과를 기록 | 성공 안내가 실제 저장 목록·파일 등록의 제외 개수와 일치하는지 검토. 연타 방지는 버튼 비활성화뿐 아니라 요청이 1회만 전송됐는지까지 확인 |

확정한 spec·plan과 [공통 개발 규칙](AGENTS.md)을 AI 작업의 기준으로 전달하고, 테스트 기대값은 spec의 기대 동작에서 가져오도록 했습니다. 요청 이력과 처리 결과를 추적하는 자동 복구는 별도 설계·검증이 필요해 이번 범위에서 제외했습니다.

## 7. 확인 결과와 남은 일

### 7.1. 구현·검증 결과

질문이 중복 저장되거나 사라지는 조건과 실패 후 입력 보존을 우선 확인했습니다. 입력·요청 처리는 API·MSW를 연결한 화면 테스트로, 새로고침 후 유지·면접 연결은 실제 빌드의 브라우저에서 검증했습니다.

| 확인 항목 | 기대 결과 | 실제 결과 |
| --- | --- | --- |
| 직접 입력·편집의 빈 값·중복 | 저장 거절, 입력 유지 | 저장되지 않았고 입력 유지 |
| 파일 등록 | 확인 후 저장, 개수·제외 사유 안내 | [4.2절 예시](#42-핵심-흐름-확인)의 등록 1·중복 2·오류 1이 화면·저장 결과와 일치 |
| 미리보기 후 같은 질문 등록 | 저장 시 최신 데이터로 재검사 | 등록 가능 2개 → 실제 1개 추가·1개 중복 안내 |
| 지연·실패·재시도 | 연타 차단, 실패 시 입력 보존 | 연타는 요청 1회, 실패 후 입력 유지·사용자 재시도 때만 총 2회 |
| 저장 후 목록 갱신 실패 | 저장 성공 유지, 조회만 재시도 | 성공 안내 유지, 새로고침은 GET만 전송 |
| 등록 → 새로고침 → 면접 시작 | 질문 유지, 선택한 질문으로 시작 | 실제 빌드의 Chromium E2E에서 유지·면접 시작 확인 |
| 특수 이름의 카테고리 | 이름에 관계없이 등록·삭제 개수 반영 | `__proto__`·`constructor`·`toString` 모두 0 → 1 → 2 → 삭제 후 1 확인 |

타입·관련 테스트·변경 코드 린트·빌드는 통과했습니다. 전체 린트는 기존 녹음·세션 오류 1건·경고 2건으로 실패합니다. [검사 기록](specs/001-question-management/tasks.md#51-최신-검증-결과)

요청 충돌·필터 변경·키보드·오프라인·좁은 화면의 추가 검증과 수정 전·후 결과는 [검증 기록](specs/001-question-management/tasks.md#5-구현검증-기록)에 있습니다.

### 7.2. 남은 일과 미룬 이유

| 남은 문제·사용자 영향 | 미룬 이유·후속 작업 |
| --- | --- |
| 기존 질문·카테고리가 표시되지 않아 다시 등록해야 함. 원본은 보존 | 이전은 이번 범위에서 제외. 중복 보존·실패 복구 정책을 별도로 정해야 함 |
| 파일에만 있는 카테고리는 직접 추가해야 필터 선택 가능 | 카테고리는 로컬 유지. 서버 연결 시 목록 공유 방식도 설계 필요 |
